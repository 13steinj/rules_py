# Execution-image tools and wheel processing

Load the generic API from `@aspect_rules_py//py:container.bzl`. Image selection,
compiler configuration, and wheel compatibility policy are independent. Any
execution image can be used if it provides the declared tools and `/bin/sh`
for the generated shims. Image inspection and downloads are not performed by
these rules.

## Tool declarations

`container_tools` is a repository rule. In `MODULE.bazel`:

```starlark
container_tools = use_repo_rule("@aspect_rules_py//py:container.bzl", "container_tools")
container_tools(
    name = "image_tools",
    tools = {
        "gcc": "/opt/compiler/bin/gcc",
        # Add the other C++ roles required by your configuration.
        "python": "/opt/python/bin/python",
        "wheel_processor": "/opt/tools/bin/processor",
    },
    args = {"gcc": ["-fPIC"]},
    env = {"PATH": "/opt/compiler/bin:/usr/bin:/bin"},
    cc_toolchain_config = "//build:compiler_config",
)
```

Each entry becomes a public executable source label such as
`@image_tools//:gcc`. It exports the explicit environment, then executes the
image tool with fixed arguments followed by action arguments. Values are
quoted literally; paths can also be command names resolved through the
configured `PATH`. The scripts are declared action inputs, so changes to
their paths, arguments, or environment invalidate dependent actions.

The optional `cc_toolchain_config` attribute is needed only for C++. It points
to the configuration generated by `container_cc_toolchain`, whose target name
has `_config` appended. For example, `container_cc_toolchain(name = "compiler",
...)` in `//build` matches the declaration above. The repository owns the
`cc_toolchain` implementation beside its shims, keeping tool paths normalized
without host paths or `../` escapes.

`container_cc_toolchain(name, tools, target_compatible_with,
exec_compatible_with, **cc_config_options)` maps standard C++ tool roles
(`gcc`, `ar`, `ld`, etc.) to labels from that repository. Supply the Unix C++
configuration attributes explicitly, including CPU, compiler, ABI, system
include directories, language standard, and runtime linkage. All C++ shims
must come from the same `container_tools` repository. No architecture,
compiler installation, or static-runtime policy is built into this macro.
See [the complete example](../e2e/manylinux/toolchains/profiles.bzl).

For other actions, `container_toolchain(name, tools = {label: role})` produces
`ToolchainInfo` with executable files by role. Register it using
`@aspect_rules_py//py/container:toolchain_type` and the desired execution
constraints. Source shims and executable rules with data/runfiles are both
supported; those files and runfiles trees are declared action inputs.

## Wheel processor contract

`py_wheel_process` accepts:

- `wheel`: a target providing `PyWheelInfo`.
- `platform`: the target platform for the wheel's full native dependency graph.
- `processor_args`: arguments with `{wheel}` and `{output_dir}` placeholders.
- `platform_tag`: the expected output platform tag, possibly dot-compressed.
- `python_tool` and `processor_tool`: role names in the selected container
  toolchain, defaulting to `python` and `wheel_processor`.
- Standard rule attributes, including `exec_compatible_with` for image selection.

The small Python adapter stages the canonical input filename recorded in
`PyWheelInfo`, invokes the declared processor, and publishes its one output
wheel plus canonical name file. This is necessary because Bazel declares
output paths before stamped wheel names and processor-added aliases are known.
Python is an explicit execution tool, not an assumed image path. The adapter
uses only its standard library.

The processor must write exactly one wheel to `{output_dir}` and preserve the
input distribution, version, build tag, Python tag, and ABI tag. The adapter
checks output filename and internal `WHEEL` tag sets against `platform_tag`;
compressed-tag ordering is immaterial. This checks the processor's output
contract, not binary compatibility. Use a processor that performs the desired
compatibility checks, such as the separate [auditwheel adapter](manylinux.md).
Export the result using `py_wheel_dist` to obtain its canonical filename.

## Platform selection

Declare ordinary Bazel platforms with
`exec_properties = {"container-image": "docker://...@sha256:..."}`. Distinct
build-environment constraints let two profiles of the same OS/libc use different
tools. Register the ordinary host execution platform first. Constrain existing
host C++ toolchains to the ordinary target environment; an unconstrained C++
toolchain could otherwise satisfy an image target on the host.

Use a constraint setting with a host default to preserve existing platforms.
Disable Bazel's auto-detected C++ fallback with
`common --repo_env=BAZEL_DO_NOT_DETECT_CPP_TOOLCHAIN=1` when explicitly registering
all C++ toolchains. Set the wheel rule's `platform` and `exec_compatible_with`
consistently. Code generators and wheel assembly can continue to run on the
host. Python headers must match the wheel ABI, and sources must support the
selected image's compiler.

## Local Docker execution

With Bazel 9.1.1, use the following flags (substitute your platform labels):

```text
build:container-docker --experimental_enable_docker_sandbox
build:container-docker --noexperimental_docker_use_customized_images
build:container-docker --spawn_strategy=worker,sandboxed,docker,local
build:container-docker --allowed_strategies_by_exec_platform=//:manylinux_2_28=docker
build:container-docker --allowed_strategies_by_exec_platform=//:manylinux2014=docker
```

The allowlist restricts only actions assigned to those execution platforms.
Other actions keep their normal worker/sandbox/local strategies, even when
they have the same mnemonic. Image actions fail if Docker is unavailable;
they cannot silently fall back to a host compiler. Do not set a global
`--experimental_docker_image` or route all `CppCompile` actions to Docker.

Bazel's experimental Docker strategy may pull a missing image. Fetch the
pinned images explicitly before builds when downloads must be controlled.
Disabling customized images keeps the actual execution image identical to
the digest used for remote execution and avoids rebuilding it for each UID.

## Remote execution

Use the same platforms and toolchains, configure your `--remote_executor`,
and replace the Docker flags with:

```text
build:container-remote --spawn_strategy=remote,worker,sandboxed,local
build:container-remote --allowed_strategies_by_exec_platform=//:manylinux_2_28=remote
build:container-remote --allowed_strategies_by_exec_platform=//:manylinux2014=remote
```

The executor must honor `container-image` and provide the pinned image.
Host generators still require an execution platform appropriate to your
executor. The processor action uses its declared image tools and needs
no network access. This example is validated locally with Docker; a remote
service must be validated against its own scheduling and image policy.
